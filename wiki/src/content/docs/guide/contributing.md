本Wiki使用Astro Starlight内容页。本地编辑Markdown，预览并检查后，再通过项目的发布流程更新站点；网页上没有匿名编辑入口。

## 新增或修改页面

内容存放在站点工程的 `src/content/docs/`。文件夹用于组织主题，例如 `world/overview.md` 对应 `/world/overview/`。先寻找现有页面，避免让同一母舰或技术设定出现两个互相冲突的版本。

每页使用以下结构；正文从说明或二级标题开始，不重复顶层标题：

```markdown
---
title: 页面标题
description: 简短说明本页的对象、用途或状态。
---

先说明这项设计是什么，以及目前完成到哪里。

## 设计关系

补充必要的图示、取舍和下一步。
```

链接采用站点路径，例如 `[母舰总览](/ship/overview/)`，不要引用作者电脑上的目录或临时预览地址。

## 图像与说明

每张 AI 手稿必须同时保存实际输入的完整提示词。记录在 `src/data/prompt-records.json`，逐图标注初始生成、每次编辑指令和参考图关系；不以概括、翻译或事后补写替代原始输入。历史版本也需要记录。

图文页使用 MDX 和 `ArtFigure` 组件，让图片与提示词一起出现，例如：

```mdx
import ArtFigure from '../../../components/ArtFigure.astro';

<ArtFigure image="/art/current/01-master-study.png" alt="归航号母舰概念手稿：主轮廓与双港关系" />
```

导入路径随页面位置调整。组件会自动读取这张图的生成记录，提供完整原文、修订顺序和复制按钮；遗漏记录会阻止构建。所有版本也会进入[逐图提示词索引](/prompts/)。

替代文字说明图片表达的内容；正文交代它是主视图、拆解图、功能示意还是气氛探索。不能因为文件名叫“多视图”，就把生成图写成精确工程投影。

修改图片时保留版本关系：当前页指向当前修订，旧版进入归档，评审记录写明改动和仍未解决的部分。图片上的数字、箭头、编号和左右关系都需要人工核对。

## 写清状态与来源

科技纪年、人口和尺寸尚未确定时，直接标“候选”；已经画出但未制作进游戏时，标“已绘制，未实现”。不要把“看起来能够通过门口”改写成“通行验证通过”。

公开参考优先链接作者、制作方或机构的原始页面，并说明实际借鉴的是哪种关系。不要上传他作素材来充当本作资产，也不要复制私人资料、账号信息、密钥、原始运行日志或未公开的内部文档。

## 发布前检查

1. 阅读页面本身，确认标题、说明、状态与正文一致。
2. 检查内部链接、图片路径、替代文字以及手机宽度下的表格和图注。
3. 将新图与相关旧图并排核对，重点检查数量、方向、接口、人物尺度和压力边界。
4. 在[评审页](/process/reviews/)记录具体问题。局部修正与整体通过分开写。
5. 使用站点项目提供的预览和构建命令完成检查，再按既定发布流程更新。

维护记录应让下一位制作成员知道“依据是什么、改了哪里、还差什么”。增加页数不是完成设计的替代品。
